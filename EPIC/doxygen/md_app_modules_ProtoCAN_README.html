ProtoCAN

ProtoCAN は、CAN バス通信上でプロトコルバッファを使用したデバイス間通信を実現する C++ ライブラリです。1000行のコードで、型安全性と柔軟性を両立させた通信システムを提供します。

設計思想と概念

CANバスは本質的にブロードキャスト通信です。送信されたメッセージは物理的に全ノードに届き、各ノードはCAN IDを見て自分宛かを判断します。この特性を抽象化で隠すのではなく、型システムで表現することで、中央集権型から完全分散型まであらゆるネットワーク構成に対応できる設計になっています。

ProtoCANはMasterとDeviceという2つのAPIを提供しますが、これは物理的な制約ではなく使いやすさのための概念的な分類です。Masterは任意のデバイスに命令を送り、任意のデバイスからデータを受信します。DeviceはDeviceIDを持ち、自身のデータを送信し、自分宛の命令を受け取ります。しかし、DeviceIDを持つノードが他のデバイスに命令を送ることも、MasterがDeviceIDを持って自身のデータを送信することも自由です。一つのノードがMasterとDeviceの両方のAPIを使って複数の役割を果たすことも自然にできます。具体的には使用するネットワーク構成の型に依存します。

ProtoCANは現在4種類のメッセージタイプを定義しており、将来さらに追加可能です。「制御命令(Command)」は特定のDeviceIDに向けた操作指示、「データ送信(Data)」はDeviceIDを持つノードからの状態報告、「要求命令(Request)」は状態情報の問い合わせ、「応答送信(Reply)」はRequestに対する返答です。この中でCommandとDataだけが特殊で、デバイス種類ごとに異なるProtocol Buffersスキーマを使用します。RequestやReplyなど他のメッセージタイプは全デバイス共通のスキーマです。

型安全性はDeviceIDのテンプレート化とデバイスカタログにより実現されています。DeviceID<DeviceType::MOTOR>という型情報により、そのデバイスが使用するDataスキーマとCommandスキーマがコンパイル時に決定されます。デバイスカタログがDeviceTypeと各スキーマを紐付けるため、IDEの補完機能も効き、新しいデバイス種類が増えてもタイプセーフに扱えます。

Quick Start

apiフォルダに全てのAPIのコードがある。 can/fdどちらも対応しているが拡張CANIDを使用しているためextを含むprofile以外使えない FdCanCompatExtProfile、CanExtProfileなど。

以下はlocal環境で実行して見る例である。これはtestコードの先頭2つを通常実行可能にしたものだ。 以下のファイルをtest/scratch/protocan.cppに保存し、 app/test/にてmake gen_protoとmake scratch FILE=tryより実行することが可能。

#include <ProtoCAN/proto_can.hpp>
#include <CanSystem/profile/MockCanProfile.hpp>
#include <cstdio>
int main(void) {
printf("=== ProtoCAN Quick Start ===\n\n");
// Step 1: デバイスの初期化
printf("Step 1: Initializing devices...\n");
CanSystem::MockCanProfile mock;
mock.enableLoopback(); // ループバックで送受信をシミュレート
PC::Messenger messenger(mock);
PC::DeviceID<PC::DeviceType::MOTOR> device(15);
PC::Master master(messenger);
PC::Device motor(messenger, device);
printf(" ✓ Master and Motor device (ID=15) initialized\n\n");
// Step 2: Data送受信 - Deviceからの状態データ配信
printf("Step 2: Device Data transmission...\n");
devices::motor::Data data;
data.set_speed(1200);
motor.send_data(data); // モーターが状態データを送信
printf(" → Motor sent data: speed = %d\n", data.speed());
auto data_opt = master.get_data(device); // Masterが受信
if(data_opt.has_value()) {
auto motor_data = *data_opt;
printf(" ✓ Master received data: speed = %d\n\n", motor_data.speed());
} else {
printf(" ✗ Failed to receive data\n\n");
return 1;
}
// Step 3: Command送受信 - Masterからの制御コマンド
printf("Step 3: Master Command transmission...\n");
devices::motor::Command cmd;
cmd.set_speed(2000);
master.send_command(device, cmd); // Masterがコマンドを送信
printf(" → Master sent command: speed = %d\n", cmd.speed());
auto cmd_opt = motor.get_command(); // Motorが受信
if(cmd_opt.has_value()) {
auto motor_cmd = *cmd_opt;
printf(" ✓ Motor received command: speed = %d\n\n", motor_cmd.speed());
} else {
printf(" ✗ Failed to receive command\n\n");
return 1;
}
printf("=== All steps completed successfully! ===\n");
return 0;
}

詳細設計

レイヤー構造と責務

ProtoCANは3つのレイヤーで構成され、各レイヤーは明確に分離された責務を持ちます。

**API層**は、デバイス種類(DeviceType)とメッセージ種類(MessageType)の2つの情報からスキーマを特定します。DataとCommandはデバイスカタログを参照してコンパイル時に型を決定し、RequestやReplyなど他のメッセージ種類は全デバイス共通スキーマとしてハードコードされています。スキーマ型とメッセージオブジェクトをそのままMessenger層へ渡します。

**Messenger層**は、受け取った型付きメッセージオブジェクトをProtocol Buffersでシリアライズし、rawバイトデータに変換してFrameLayer層へ渡します。受信時は逆に、FrameLayer層から受け取ったrawバイトデータを指定された型でデシリアライズします。send<T>(MessageID, T data)とread<T>(MessageID, T& data)というテンプレート関数により、型安全性を保ちながらシリアライゼーションを完全にProtocol Buffersへ委譲しています。

**FrameLayer層**は、rawバイトデータとCAN拡張IDから実際のCANフレームを構築します。送信時は最大フレームサイズ(8/64byte)に応じてデータを分割し、header-flagを設定してCanSystemへ渡します。受信時は複数フレームを同一メッセージIDでキャッシュし、size分のデータが揃ったら結合してMessenger層へ返します。フレーム欠損検出も担当し、新しいheaderフレームが来た際に前のメッセージが未完成なら破棄します。

CAN拡張ID(29bit)に全てのルーティング情報を詰め込むことで、データ部分は純粋なProtocol Buffersのシリアライズデータのみになります。この分離により、シリアライズ/デシリアライズの詳細はProtocol Buffersに完全に委譲され、スキーマ変更への対応が容易です。フレーム分割も自動的に処理されるため、アプリケーションコードは最大1024byteまでのメッセージを単一の送受信として扱えます。継承階層や仮想関数は使わず、テンプレートとProtocol Buffersの組み合わせだけで拡張性を確保しています。

CANプロトコル概要

1. 概要

CAN拡張ID(29bit)とProtocol Buffersを用いたデバイス間通信システム。

対象デバイス

  • モータ操作基盤
  • センサー基盤 など

各デバイスタイプごとに個別の<tt>.protoスキーマファイルを用意。coreと共有して持つ。

2. CAN拡張ID構成(29bit)

[version 2bit][デバイス種類ID 5bit][デバイス番号ID 4bit][message type 4bit][flags 4bit][size 10bit]

DeviceID定義

  • 完全なDeviceID = [デバイス種類ID 5bit][デバイス番号ID 4bit] (9bit)
  • 最大512デバイス (32種類 × 各16台)
  • デバイス番号は4P DIPスイッチで基盤から設定する

フィールド詳細

フィールド ビット幅 範囲 説明 未使用
version 2bit 4つ プロトコルバージョン 3つ
デバイス種類ID 5bit 32個 -
デバイス番号ID 4bit 16個 4P DIPスイッチで設定 -

3. メッセージ種類

メッセージ種類 message type 送信元 送信先 スキーマ
制御命令 0000 core device (個別/全体) 各デバイスごとの命令スキーマ
データ送信 0001 device core 各デバイスごとの送信スキーマ

制御命令 でデバイスを制御
データ送信でデバイスのデータを送信
状態要求命令に対して応答送信が送られる

DeviceIDとメッセージ種類でスキーマを特定できる必要がある。

4. プロトコル動作

フレーム構造

CANフレーム構成

  • フレーム = [CAN拡張ID 29bit][データ 8/64byte]
  • メッセージID = [vertion][DeviceID][メッセージタイプ] 15bit

拡張IDに全てのヘッダ情報が含まれるため、データは純粋にProtocol Buffersのシリアライズデータのみを格納する。

フレーム分割

単一フレーム

  • データが8/64Byte以下のときは単一フレームで送信する
  • header-flag=1で送信

分割フレーム時

  • 単一frameに収まらないデータは複数に分割され同一メッセージIDを使い連続送信される
  • header-flag=1のフレームはメッセージの先頭フレーム
  • header-flag=0のフレームは継続データを示す
  • メッセージIDが異なるフレームは独立したメッセージとして扱われる

このフレーム分割より最大1024Byteまで送信可能になる。(sizeが10bitのため)

欠損検出

同一メッセージIDで、受信データ量がsize未満の状態で新たにheader-flag=1のフレームを受信したとき、前のメッセージ欠損したことになる。
あるメッセージを受信している間他のメッセージを受信しても順序は保たれるためすべて追跡していれば問題ない。

特徴

  • CAN IDのみで全ヘッダ情報を取得可能
  • シリアライズ/デシリアライズの詳細はProtocol Buffersに委譲
  • CAN標準(8byte) / CAN-FD(64byte)両対応
  • CAN拡張IDとprotocol bufferはarduinoでも使える
  • 構築: 1.9.5
