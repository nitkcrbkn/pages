STM32 マイコン用のロボット制御システム。HAL 依存を分離したモジュラーアーキテクチャを採用し、ロギング・CAN 通信・デバッグストリーム機能を提供する。

Quick Start

環境構築から STM32 への書き込み、動作確認までの手順を示す。 STM32CubeIDEを使用する方法とdockerビルド環境を使う方法がある。 dockerのほうがサポートしてされてるがSTM32CubeIDEでは動かない可能性がある。

docker

clone

git clone https://github.com/nitkcrbkn/STM32System
git submodule init
git submodule update

dockerビルド環境のビルド

stm32-docker-flashのrepoにコードがある。 このプロジェクトではstm32-docker-flash/README 詳細が書かれているが、細かい動作は[Makefile](Makefile)の基準によって変わる。

cd app/lib/stm32-docker-flash
docker build -t stm32-flash .

STM32用プロジェクトビルド

docker run --rm -v $(pwd):/workspace \
stm32-flash bash /app/build.sh

書き込み

docker run --rm -v $(pwd):/workspace \
--privileged --device=/dev/ttyACM0 \
stm32-flash bash /app/flash.sh

Debug

以下のコマンドでTUIのデバッガを開く。IDEのデバッガを使用する方法はREADMEを確認。

docker run --rm -v $(pwd):/workspace \
--privileged --device=/dev/ttyACM0 \
stm32-flash bash /app/debug.sh

CubeIDE

1. プロジェクトのクローンとセットアップ

git clone https://github.com/nitkcrbkn/STM32System

2. STM32CubeIDE でプロジェクト作成

File -> Import -> Import from existing STM32CubeMX configuration File (.ioc)

3. コードの移動と設定

  • 新しく生成された CubeIDE 管理下の STM32System/ に、clone した repo の .git/ を移動
  • IDE または console で目的のブランチへ checkout

  • submodule を更新:

    git submodule init
    git submodule update

  • main.c に以下を追加:

    {c++}
    /* USER CODE BEGIN PFP */
    void app_main(void);
    /* USER CODE END PFP */
    {c++}
    /* USER CODE BEGIN WHILE */
    app_main();
    /* USER CODE END WHILE */

4. コード生成とビルド

CubeMX (CubeIDE 組み込み) で .ioc を開き、code generation を実行する。

5. STM32 への書き込み

  • STM32 を接続
  • STM32CubeIDE -> Project Explorer -> right click -> Run as -> STM32 C/C++ Application

STM32 との通信

  • Tera Term などの Terminal ソフトで STM32 の COM ポートを bitrate 115200 で開く
  • Break Signal を送信して再起動する

TEST

testについてはapp/test/README.mdを確認すること。

Usage Guide

各モジュールの基本的な使い方を示す。詳細な API 仕様は doxygen を参照のこと。

Include Path

module および lib は include に含まれているため <logic/> などで include 可能。 追加の include が必要な場合は以下の設定を行う。 Project -> Properties -> C/C++ build -> setting -> MCU/MPU GCC compiler -> include paths ここに Debug/folder からの相対パスを追加する（例: ../app/lib/etl/include/）。

Clog (ロギングシステム)

printf スタイルのロギングと色付き出力機能を提供する。

基本的な使い方

各 project ごとに Logger.hpp を logic/ に配置する。ここでマクロ API の生成と設定を行う。 CLog::LogDirector& get_logger() により最低の loglvl と出力先（複数可）を設定できる。

ロギングマクロ

マクロ log lvl
LOGD debug
LOGI info
LOGW warning
LOGE error

使用方法: LOG*(const char* format, ...)

  • printf と同様に C 言語 format が利用可能
  • マクロ内で cTag のコンパイル時検証と cformat を実行する

色付きログ

パイプ (|) と Color Tag（cTag）で文字色を指定可能。 使用可能な色は log_type.hpp の ASCII_COLORS を参照する。

使用例:

{c++}
LOGI("g|green text| normal text y|yellow|");

バリデーション:

  • コンパイル時: パイプの偶数個チェック、cTag が 0-1 または a-z かを検証
  • ランタイム時: cFormat 後の文字列についてパイプと cTag を検証

STREAM (split screen)

複数チャンネルのリアルタイムデータを画面に対して指定行へ固定表示する。通常の LOG と共用可能。

セットアップ

起動時に必ず以下を実行する。

{c++}
STREAM_SETUP(CH_COUNT); // config.h の enum LogChannel の CH_COUNT を渡す

データ出力

{c++}
STREAM(CH_index, const char* format, ...);
  • config.h の LogChannel を index で指定する
  • C 言語の format が利用可能

重要な注意点

  • 接続するたびに再起動すること: 起動時のみ console format ASCII を送信する
  • 割り込み中に printf を使用しない: CAN 送受信を阻害し console format の崩れを引き起こす
  • F0 マイコンでは使用不可: 32kb の FLASH RAM 制限により lite module を利用すること

Architecture

システムの設計思想とモジュール開発者向け情報を示す。

設計思想

STM32System は HAL 依存コードと非依存コードを分離したレイヤーアーキテクチャを採用している。ただし STM32 HAL の特性上、HAL 非依存とは「HAL を直接呼び出さない」ことを意味し、完全な独立性を持つわけではない。

システムは 3 つの主要レイヤーで構成される。logic 層はビジネスロジックを担当し HAL 非依存、platform 層は HAL へのアダプタとして機能し HAL 依存、app 層はロボット制御の実装を担い HAL を直接使わず他層を経由する。

modules フォルダには複数ファイルからなる自作ライブラリ（各 module と呼ぶ）を配置する。CanSystem など HAL 依存が強い module は独立したフォルダを持つ。module/logic/ と module/platform/ には単一ファイルの小規模ライブラリを依存性に応じて配置する。lib フォルダには HAL 非依存の純粋な外部ライブラリを git submodule として配置する。

すべてのライブラリは基本的に header only で実装されており、app/appMain.cpp が唯一の非ヘッダーコードである。これにより管理を簡素化し、ArduinoSys との互換性を高めている。

フォルダ構造とレイヤーの対応

path layer HAL 依存 説明
app/ app 層 無し ロボット制御コード（appMain.cpp 等）
app/module/logic/* logic 層 無し 単一ファイルのビジネスロジックライブラリ
app/module/platform/* platform 層 有り 単一ファイルの HAL アダプタライブラリ
app/modules/*/ （※） 混在 複数ファイル構成の自作ライブラリ（module）
app/lib/ logic 層 完全無し 外部ライブラリ（git submodule）

※ logic と platform が混在する場合あり

レイヤー詳細

レイヤー名 責務 依存ルール 配置基準
app 層 ロボット制御フロー実装、初期化処理とメインループ logic 層、platform 層に依存可。HAL 直接呼び出し不可 appMain.cpp、config.h
logic 層 ビジネスロジック、アルゴリズム、データ処理 他 logic 層、外部ライブラリのみ依存可。HAL 依存不可 HAL を使わない汎用的な処理
platform 層 HAL へのアダプタ、ハードウェア抽象化 logic 層、HAL に依存可 HAL API を直接呼び出す必要がある処理

モジュール開発

用語の定義

  • ライブラリ: 再利用可能な機能をまとめたコード集合。単一ファイルまたは複数ファイルで構成される。基本的に header only で実装
  • modules（フォルダ）: app/modules/ ディレクトリ。複数ファイルからなる自作ライブラリを配置
  • module（ライブラリ）: modules/ 内の各独立フォルダ（例: CanSystem/）。複数のソースやヘッダーで構成され特定の機能を提供する単位
  • logic/（フォルダ）: app/module/logic/ ディレクトリ。HAL 非依存の単一ファイルライブラリを配置
  • platform/（フォルダ）: app/module/platform/ ディレクトリ。HAL 依存の単一ファイルライブラリを配置
  • lib/（フォルダ）: app/lib/ ディレクトリ。git submodule として管理される外部ライブラリを配置。すべて HAL 非依存
  • 単一ファイルライブラリ: 1 つの .h や .hpp ファイルで完結する小規模ライブラリ。module/logic/ または module/platform/ に直接配置
  • 複数ファイルライブラリ: 複数ソースで構成される中〜大規模ライブラリ。独立したフォルダ（module）として管理

新規モジュール追加

  1. 配置場所の決定 単一ファイルライブラリ:

    • HAL 非依存 → app/module/logic/
    • HAL 依存 → app/module/platform/

    複数ファイルライブラリ:

    • 自作ライブラリ → app/modules/<module名>/（独立フォルダとして管理）
    • 外部ライブラリ → app/lib/<module名>/（git submodule として追加）
  2. インクルードパスの追加 必要に応じて以下を設定する。 Project -> Properties -> C/C++ build -> setting -> MCU/MPU GCC compiler -> include paths Debug/folder からの相対パスで追加（例: ../app/lib/etl/include/）

  3. **git submodule 管理**（外部ライブラリの場合）

    git submodule add <repository-url> app/lib/<module-name>
    cd app/lib/<module-name>
    git fetch
    git checkout <target branch>

Best Practices / Guidelines

ライブラリ開発とコード記述における推奨事項をまとめる。

コーディング規約

命名規則:

  • クラス/構造体: PascalCase（例: CanController, LogDirector）
  • 関数/変数: snake_case（例: init_can(), log_level）
  • 定数/マクロ: UPPER_SNAKE_CASE（例: MAX_BUFFER_SIZE, LOGD）
  • ファイル: snake_case.hpp（例: can_system.hpp）
  • フォルダ: snake_case または PascalCase（例: logic/, CanSystem/）

ファイル拡張子:

  • .hpp: C++ ヘッダー（クラス、テンプレートを含む）
  • .h: C 互換ヘッダー（extern "C" リンケージ用）app_main.h だけ

インクルードガード:

#pragma once

ライブラリ実装方針

Header-only 原則:

  • 基本 header-only で実装し、appMain.cpp 以外に .cpp を作らない

依存関係の明示:

  • header-only で技術的に不要でも依存ファイルをすべて #include する
  • 可読性と依存関係の可視化を優先する

HAL 依存の分離:

  • HAL 非依存の場所（logic 層、lib/）では HAL を直接呼ばない
  • 必要な場合は platform 層を経由する

インスタンス管理:

  • イミュータブルなインスタンスはポインターでなく参照（&）で管理する
  • コピーコストを削減し所有権を明確にする

インターフェースの使用:

  • #ifdef の多用や複数クラスで同じ形式の結果を返す場合は抽象インターフェースを使用し可読性を高める
  • 例: ICanController で CAN/FDCAN の差異を吸収する

コールバック実装:

  • 初期実装: <platform/Callbacks.h> に HAL 提供の weak 関数を記述
  • 柔軟性が必要な場合: クラス内で自動コールバック登録/検索機能を実装

エラー処理

戻り値:

  • bool 型で成功/失敗を返す
  • エラー時は必ず LOGE() を用いてログ出力する

例外処理:

  • try/catch など例外機構は使用しない
  • コードサイズと実行時オーバーヘッドを削減する

ログ出力:

  • エラー発生時は必ず LOGE() でエラー内容を記録する
  • デバッグ情報として原因特定に利用する

メモリ管理

動的確保の禁止:

  • new/delete, malloc/free を使用しない
  • メモリフラグメンテーションと予測不能な挙動を回避する

スタック使用:

  • 大きな配列は static またはグローバルに配置する
  • スタックオーバーフローを防止する

STL 制限:

  • F0 マイコン: ETL（Embedded Template Library）の使用を必須とする
  • 他マイコン: STL 使用可（将来的に ETL へ移行予定）

F0 マイコンの制限

F0 マイコンは 32KB の FLASH ROM 制約があるため、通常の CanSystem や Clog ではなく lite module を使用する（詳細は module/lite/README.md を参照）。

lite module を使用しても機能追加により 32KB に近づくと HardFault エラー（強制停止）が発生する場合がある。F0 マイコンでは STL を避け ETL の使用を推奨する。

パフォーマンス

割り込み内処理:

  • 処理は最小限に抑える
  • メモリ操作や再割り込みを発生させる処理（delay() など）は強制停止につながる
  • printf は非推奨

詳細実装

Clog 実装詳細

  • 各 project ごとに Logger.hpp を配置し設定と API 提供が行われる
  • マクロ API はコンパイル時とランタイム時の二段階で検証を行う
  • cTag（Color Tag）により色付きログを実現する
  • 現状は自由度が高すぎるため今後変更予定

CanSystem 実装詳細

インターフェース設計:

  • ICanController: CAN/FDCAN 共通の基本インターフェース
  • IFdcanMgr: FDCAN 固有機能
  • ICanMgr: CAN 固有機能

実装構造:

  • CanInterfaces.hpp: 全関数プロトタイプ
  • abstract/: 実装コード（命名変更予定）
  • impl/: profile 定義（CAN 割り込み設定、TxHeader、sFilterConfig）

デフォルト profile:

  • CAN: 全 ID パス設定
  • FDCAN: 全 ID パス設定
  • FDCAN 互換 CAN: 全 ID パス設定

カスタム profile: 新規作成するか、既存 profile の config を取得・編集・再適用する

ライブラリ内使用

  • ICanController&: CAN/FDCAN 共通機能（推奨）
  • IFdcanMgr& または ICanMgr&: プロトコル固有機能を追加利用可能

ICanController を使用することで CAN/FDCAN に依存しない汎用ライブラリを実現できる。
