STM32 マイコン用のロボット制御システム。HAL 依存を分離したモジュラーアーキテクチャを採用し、ロギング・CAN 通信・デバッグストリーム機能を提供する。

Quick Start

全体構造の概要

STM32System は各ロボットプロジェクトに **git サブモジュールとして app/ に配置**して使う共有ライブラリである。
そのため、STM32を用いた開発はこのリポジトリ内のコードだけでは完結しない。具体的には以下のパーツがシステムを構成する。

  • STM32 HALドライバ
    STM32に関する基本機能を提供するソフトウェア。STマイクロが提供しており、マイコンボードごとの差を吸収してくれる。
    チップとピンレイアウトごとにそれぞれ個別で<tt>.iocファイル(設定ファイル)が必要であり、これをターゲットと呼ぶ。
  • STM32System
    このrepoであり、STM32 HALドライバを利用しロボットの制御に関する様々な機能をSTM32上で実現するシステム。
    ロギングやPID制御、各種モーターへの指令を送るライブラリなどで構成される。
  • ビルド&書き込みシステム
    STM32 HALドライバ + STM32System をビルドしSTM32へ書き込む役割を持つ。
    dockerベースのstm32-docker-flashを使用する。

これらのパーツを適切に配置した上でファイルを編集・コマンドを実行する必要がある。
そのため、STM32Sysの開発・ロボットのプログラム開発・動作確認・書き込み等あらゆる操作は、STM32Sysを持つrepoで行う。一般の実験やテストはSTM32_node リポジトリを使用する(このQuickStartでもSTM32_nodeリポジトリで例示する)。

ソフトのインストール

Docker、STM32CubeMX、シリアルモニタが必要である。 OSはLinuxであれば良い、Windows11でWSL環境のUbuntuがあるものとしている。 ただし直接Linuxを使用したほうが楽。

CubeMX

STM32CubeMXは、公式サイトからダウンロードする。CubeMX2は互換性がない。
MySTへのログインが求められたりしてめんどくさいが、自分のOSに合わせたものを選択してダウンロードする。
zipファイルをダウンロードしたら解凍し、中に入っているSetupSTM32CubeMX-(バージョン名)を実行する。当然、バージョン名のところはバージョンによって異なる。

sudo apt install unzip
unzip SetupSTM32CubeMX-(環境によって変わる).zip
./SetupSTM32CubeMX-(バージョン名)

GUIが出てくるので、後は同意とnextを繰り返す。

シリアルモニタ

コマンドラインで使用できるpicocomを導入する。
Windowsの場合は、シリアルモニタにTeraTermを使用すれば良い。

sudo apt install picocom

実行には以下のコマンドを使用する。抜けるときはCtrl+A → Ctrl+Xである。

sudo picocom -b 115200 /dev/ttyACM0

~/.bashrc(Ubuntu標準)または~/.zshrcに以下のように記載することで、clogと入力するだけで開くことができ便利である。/dev/ttyACM0を記載しないことで、柔軟性を上げるのもありである。

alias clog="sudo picocom -b 115200 /dev/ttyACM0"

docker

以下のコマンドをターミナルで実行する。Dockerの競合するパッケージを一度削除するが、既存のイメージ、コンテナ、ボリューム、ネットワークは削除されない。

sudo apt remove $(dpkg --get-selections \
docker.io \
docker-compose \
docker-compose-v2 \
docker-doc \
docker-buildx \
podman-docker \
containerd \
runc |
cut -f1)
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL \
https://download.docker.com/linux/ubuntu/gpg \
-o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y --no-install-recommends \
docker-ce \
docker-ce-cli \
containerd.io \
docker-buildx-plugin

これで導入が終わるはず。終わったら、以下を実行する。

sudo systemctl status docker

これでactive (running)と表示されれば起動している(qキーで抜けられる)。止まっている場合、

sudo systemctl start docker

で解決する。テスト用コンテナを試しに動かしてみると、

sudo docker run hello-world

でHello from Docker!から始まる長文が出れば成功である。毎回sudoを使うのがめんどくさいということであれば、

sudo usermod -aG docker "$USER"

を実行してログアウト→サインインを行う。共有のPCでは推奨されない。ここから先の説明ではsudoを省略する。

使用方法

環境構築から STM32 への書き込み、動作確認までの手順を示す。 ビルド・書き込み・デバッグは docker ベースのstm32-flashツールに統一されている。 STM32CubeIDEはサポートされていない。 ここではstm32sysをすでに持つプロジェクトのrepoを使用する方法について示す。新規repoの作成は新規repo作成を参照のこと。

clone

submodule含めてクローンする。

git clone --recurse-submodules https://github.com/nitkcrbkn/STM32_node.git
cd STM32_node

もし間違って普通にcloneしてしまった場合は

cd STM32_node
git submodule update --init --recursive

dockerビルド環境のビルド

stm32-docker-flashのrepoにコードがある。 このビルドシステムの詳細はstm32-docker-flash/READMEに書かれている。

cd app/lib/stm32-docker-flash
docker build -t stm32-flash .

ホストの stm32-flash コマンドは、このイメージを docker run するラッパーである。 ~/.bashrc(Ubuntu標準)または~/.zshrcの末尾に以下を追加することで、以降は stm32-flash <command> として利用できる。複数デバイス同時接続でのデバイスの指定書き込みはサポートしていない。

alias stm32-flash='docker run --rm -it -v $(pwd):/workspace --privileged --device=/dev/ttyACM0 --network host stm32-flash'

zshでのTAB補完版のエイリアスはstm32-docker-flash/READMEに書かれている

stm32-flash --help

と打つことでヘルプを見ることができる。

HALを生成する

STM32CubeMXを起動し、File → load projectからSTM32_node(或いは別途用意したリポジトリ)内の使用するチップのディレクトリ内の<tt>.iocファイルを選択する。
例えば、STM32_nodeリポジトリ内でSTM32G474REを使うのであればG4/g4_node_dev.iocを選択する。このファイル名は、プロジェクト名及び使用するマイコンで決定される(詳細は新規repo作成の項を参照のこと)。

警告が出たらcontinueで継続する。初回などダウンロードが発生する場合や、STアカウント関連の諸々、ライセンスの同意などがある場合があるので適宜進める。
完了したら、右上のGENERATE CODEをクリックしてコードを生成する。これでHALの生成は完了である。

次に，HALで生成したコードとSTM32Sysを連携させる。チップのディレクトリ/Core/Src/main.cを開く。ここでいうチップのディレクトリとは先程HALを生成したディレクトリのことである。CubeMXによるコードの再生成後も変更が保持されるように、USER CODE BEGIN IncludesとUSER CODE END Includesの間へapp_mainの宣言を追加する。

/* USER CODE BEGIN Includes */
int app_main(void);
/* USER CODE END Includes */

また、while(1)の中，USER CODE END WHILEよりも上の部分にapp_mainの実行を入れる。

while (1)
{
app_main();
/* USER CODE END WHILE */
/* USER CODE BEGIN 3 */
}

clogスケッチのNucleoG474REへの書き込み

ルートディレクトリ(STM32_nodeリポジトリを使っているならばSTM32_nodeディレクトリ)で以下のコマンドを実行する。

stm32-flash flash -t G4 -k app/examples/clog

これは、G4をターゲットにし、exampleスケッチの1つであるclogをビルド・書き込みするコマンドである。STMが生きているかどうかの確認など基本的な動作確認にはこのclogがオススメである。 うまく書き込めない場合は少し下の「よくあるトラブルシューティング」を参考のこと。

NucleoG474REに書き込んだ上で、picocom等のシリアルモニタを起動(設定済みならばclogコマンド)し、Nucleo上のRESETボタンを押すことでlogが表示されれば成功である。

その他スケッチの書き込み

exampleスケッチは他にも存在し、ls app/examples/で確認ができる(このコマンドで表示されるディレクトリがスケッチ名である)。他のexampleスケッチを書き込みたい場合、

stm32-flash flash -t G4 -k app/examples/<スケッチパス>

でビルドが可能である。また、G4を別のチップに置き換えることで別のチップにも書き込むことができる(もちろん、CubeMXでのHAL生成はチップごとに行う必要がある)。

そして、実際の開発においてはsketchesディレクトリにスケッチを配置する。

stm32-flash flash -t G4 -k <スケッチパス>

とすることでビルドと書き込みが可能である。

よくあるトラブルシューティング

うまく書き込めない場合は

stm32-flash info

を実行すると、現在接続中のSTM32が一覧表示される。この中に表示されなければ、接続の問題(USBケーブルがデータ転送に対応してないなど)である可能性がある。

2回目以降の実行ではビルドは差分のみ行うことになるが、稀に差分ビルドでは問題が生じることがある。その場合、クリーン-cオプションをつけ

stm32-flash flash -t G4 -k app/examples/clog -c

などとすれば良い。

新規repo作成

ターゲット: .iocに紐付けられて作成される。基板＊pinマッピング事に用意する。ソースコードを含まない。 スケッチ: appMain.cpp, config.h, callbacks.hを含む、ひとかたまりのアプリケーションコード。

stm32sysを使うプロジェクトは、通常複数のターゲットと複数のスケッチを持つ。最低限必要なのは、開発用のnucleo基板向けターゲットと、実基板のチップ向けターゲットの2つ。 さらにマスター・スレイブ構成などで基板またはpinマッピングが異なる場合は追加でターゲットが増えるため、この場合は合計4つのターゲットが必要になる。 stm32sysに追加したライブラリの使用例はapp/examples/に、プロジェクト固有のスケッチは./sketchesに配置することを推奨する。

CubeMX

Project名を決める。これはターゲットフォルダ名および .ioc ファイル名と同一になる。

ビルドシステムがフォルダ名の先頭部分からフラッシュ設定を判定する仕様のため、 ターゲットフォルダ名は先頭にチップ種類を示す接頭辞を付ける必要がある。 チップ種類は"アルファベット1文字 + 数字1桁"で表され、大文字・小文字は区別されない。 つまりstm32g474の最低限のプロジェクト名は g4またはG4 となり、付け足す場合は g4_something の形になる。

また、<tt>.ioc ファイルからプロジェクトがNucleoボード用かチップ実装用かを見分けられるよう、 以下の命名方式を推奨する。

[チップ種類]_[プロジェクト名]_[chip or dev]

チップ チップ種類 フォルダ名の例
stm32g474 g4 g4, G4_robomas_dev
stm32f013 f0 f0, F0_amt_chip

手順

  1. CubeMXで新規プロジェクトを、対象となるすべてのターゲット事に作成する。
  2. File -> New Project で新規プロジェクトを作成する。
  3. Commercial Part Number にMCUの型番を入力し、対象のチップ／Nucleoを選択する。
  4. IOC編集画面が開いたら Project Manager -> Project へ移動する。
  5. Toolchain / IDE を CMake に変更する。
  6. Project Name に f0_amt_dev などのプロジェクト名を入力する。
  7. Project Location で Browse を押し、新規作成したrepoを選択する。
  8. 右上の Generate でHALコードとCMakeファイルを自動生成する。

cmake

ターゲット事にstm32flashに対応させるため[ターゲット]/CMakeLists.txtを編集する。

app/lib/stm32-docker-flash/new.mdと既存のCMakeListsを参照してチップ事に書く。 チップごとにほとんど変わらず、ピンレイアウトが変わるだけであれば使い回すことも可能である。

ビルド条件やその他の設定はここで通常のようにいじる。例えば軽量化のために浮動小数点数printfを含まない、Include pathを追加等。

target handler

[ターゲット]/target_handler.hには以下の内容を含み作成する。

  • #define [target] で G4やF0など
  • # extern以下には[ターゲット]/Core/Src/main.cの/* Private variablesのすべてのハンドラーにexternをつけたものを追加

stm32-flashは指定ターゲットのtarget_handler.hを全てのC++ファイルのインクルードを追加してコンパイルするため、app_main.cpp`に書く必要はない。

#pragma once
#define [target] # スケッチでチップの違いを吸収する場合のため
#include "main.h" # すべてのHALライブラリをいれる
# extern
// app_mainがc言語のmain関数より実行できるように
#ifdef __cplusplus
extern "C" {
#endif
int app_main(void);
#ifdef __cplusplus
}
#endif

Usage Guide

各モジュールの基本的な使い方を示す。詳細な API 仕様は doxygen を参照のこと。

Include Path

modules および lib はビルドシステム（CMake）の include パスに登録されているため、<logic/...> や <CanSystem/...> のように include 可能。 追加の include パスが必要な場合は、対象ターゲットの CMakeLists.txt に target_include_directories() でディレクトリを追加する（例: app/lib/etl/include/）。

Clog (ロギングシステム)

printf スタイルのロギングと色付き出力機能を提供する。 パイプ (|) と Color Tag（cTag）で文字色を指定可能。 使用可能な色は log_type.hpp の ASCII_COLORS を参照する。

使用例:

{c++}
LOGI("g|green text| normal text y|yellow|");
STREAM(CH_index, const char* format, ...);

重要な注意点

  • 接続するたびに再起動すること: 起動時のみ console format ASCII を送信する
  • 割り込み中に printf を使用しない: CAN 送受信を阻害し console format の崩れを引き起こす
  • F0 マイコンでは使用不可: 32kb の FLASH RAM 制限により lite module を利用すること

Architecture

システムの設計思想とモジュール開発者向け情報を示す。

設計思想

STM32System は HAL 依存コードと非依存コードを分離したレイヤーアーキテクチャを採用している。ただしヘッダーオンリーであり、STM32 HALの特性上、HAL 非依存とは「HAL を直接呼び出さない」ことを意味し、完全な独立性を持つわけではない。

システムは 3 つの主要レイヤーで構成される。logic 層はビジネスロジックを担当し HAL 非依存、platform 層は HAL へのアダプタとして機能し HAL 依存、app 層はロボット制御の実装を担い HAL を直接使わず他層を経由する。

modules フォルダには複数ファイルからなる自作ライブラリ（各 module と呼ぶ）を配置する。CanSystem など HAL 依存が強い module は独立したフォルダを持つ。modules/logic/ と modules/platform/ には単一ファイルの小規模ライブラリを依存性に応じて配置する。lib フォルダには HAL 非依存の純粋な外部ライブラリを git submodule として配置する。

すべてのライブラリは基本的に header only で実装されており、各プロジェクトの appMain.cpp が唯一の非ヘッダーコードである。これにより管理を簡素化し、ArduinoSys との互換性を高めている。

フォルダ構造とレイヤーの対応

path layer HAL 依存 説明
examples/<name>/ app 層 無し ロボット制御コード（appMain.cpp 等）
modules/logic/* logic 層 無し 単一ファイルのビジネスロジックライブラリ
modules/platform/* platform 層 有り 単一ファイルの HAL アダプタライブラリ
modules/*/ （※） 混在 複数ファイル構成の自作ライブラリ（module）
lib/ logic 層 完全無し 外部ライブラリ（git submodule）

※ logic と platform が混在する場合あり

レイヤー詳細

レイヤー名 責務 依存ルール 配置基準
app 層 ロボット制御フロー実装、初期化処理とメインループ logic 層、platform 層に依存可。HAL 直接呼び出し不可 appMain.cpp、config.h
logic 層 ビジネスロジック、アルゴリズム、データ処理 他 logic 層、外部ライブラリのみ依存可。HAL 依存不可 HAL を使わない汎用的な処理
platform 層 HAL へのアダプタ、ハードウェア抽象化 logic 層、HAL に依存可 HAL API を直接呼び出す必要がある処理

モジュール開発

用語の定義

  • ライブラリ: 再利用可能な機能をまとめたコード集合。単一ファイルまたは複数ファイルで構成される。基本的に header only で実装
  • modules（フォルダ）: modules/ ディレクトリ。複数ファイルからなる自作ライブラリを配置
  • module（ライブラリ）: modules/ 内の各独立フォルダ（例: CanSystem/）。複数のソースやヘッダーで構成され特定の機能を提供する単位
  • logic/（フォルダ）: modules/logic/ ディレクトリ。HAL 非依存の単一ファイルライブラリを配置
  • platform/（フォルダ）: modules/platform/ ディレクトリ。HAL 依存の単一ファイルライブラリを配置
  • lib/（フォルダ）: lib/ ディレクトリ。git submodule として管理される外部ライブラリを配置。すべて HAL 非依存
  • 単一ファイルライブラリ: 1 つの .h や .hpp ファイルで完結する小規模ライブラリ。modules/logic/ または modules/platform/ に直接配置
  • 複数ファイルライブラリ: 複数ソースで構成される中〜大規模ライブラリ。独立したフォルダ（module）として管理

新規モジュール追加

  1. 配置場所の決定 単一ファイルライブラリ:

    • HAL 非依存 → modules/logic/
    • HAL 依存 → modules/platform/

    複数ファイルライブラリ:

    • 自作ライブラリ → modules/<module名>/（独立フォルダとして管理）
    • 外部ライブラリ → lib/<module名>/（git submodule として追加）
  2. インクルードパスの追加 modules/ と lib/ は既定で include パスに登録されている。追加が必要な場合は、対象ターゲットの CMakeLists.txt に target_include_directories() でディレクトリを追加する（例: app/lib/etl/include/）。

  3. **git submodule 管理**（外部ライブラリの場合）

    git submodule add <repository-url> app/lib/<module-name>
    cd app/lib/<module-name>
    git fetch
    git checkout <target branch>

Best Practices / Guidelines

ライブラリ開発とコード記述における推奨事項をまとめる。

コーディング規約

命名規則:

  • クラス/構造体: PascalCase（例: CanController, LogDirector）
  • 関数/変数: snake_case（例: init_can(), log_level）
  • 定数/マクロ: UPPER_SNAKE_CASE（例: MAX_BUFFER_SIZE, LOGD）
  • ファイル: snake_case.hpp（例: can_system.hpp）
  • フォルダ: snake_case または PascalCase（例: logic/, CanSystem/）

ファイル拡張子:

  • .hpp: C++ ヘッダー（クラス、テンプレートを含む）
  • .h: C 互換ヘッダー（extern "C" リンケージ用）app_main.h だけ

インクルードガード:

#pragma once

ライブラリ実装方針

Header-only 原則:

  • 基本 header-only で実装し、appMain.cpp 以外に .cpp を作らない

依存関係の明示:

  • header-only で技術的に不要でも依存ファイルをすべて #include する
  • 可読性と依存関係の可視化を優先する

HAL 依存の分離:

  • HAL 非依存の場所（logic 層、lib/）では HAL を直接呼ばない
  • 必要な場合は platform 層を経由する

インスタンス管理:

  • イミュータブルなインスタンスはポインターでなく参照（&）で管理する
  • コピーコストを削減し所有権を明確にする

インターフェースの使用:

  • #ifdef の多用や複数クラスで同じ形式の結果を返す場合は抽象インターフェースを使用し可読性を高める
  • 例: ICanController で CAN/FDCAN の差異を吸収する

コールバック実装:

  • 初期実装: <platform/Callbacks.h> に HAL 提供の weak 関数を記述
  • 柔軟性が必要な場合: クラス内で自動コールバック登録/検索機能を実装

エラー処理

戻り値:

  • bool 型で成功/失敗を返す
  • エラー時は必ず LOGE() を用いてログ出力する

例外処理:

  • try/catch など例外機構は使用しない
  • コードサイズと実行時オーバーヘッドを削減する

ログ出力:

  • エラー発生時は必ず LOGE() でエラー内容を記録する
  • デバッグ情報として原因特定に利用する

メモリ管理

動的確保の禁止:

  • new/delete, malloc/free を使用しない
  • メモリフラグメンテーションと予測不能な挙動を回避する

スタック使用:

  • 大きな配列は static またはグローバルに配置する
  • スタックオーバーフローを防止する

STL 制限:

  • F0 マイコン: ETL（Embedded Template Library）の使用を必須とする
  • 他マイコン: STL 使用可（将来的に ETL へ移行予定）

F0 マイコンの制限

F0 マイコンは 32KB の FLASH ROM 制約があるため、通常の CanSystem や Clog ではなく lite module を使用する（詳細は modules/lite/README.md を参照）。

lite module を使用しても機能追加により 32KB に近づくと HardFault エラー（強制停止）が発生する場合がある。F0 マイコンでは STL を避け ETL の使用を推奨する。

パフォーマンス

割り込み内処理:

  • 処理は最小限に抑える
  • メモリ操作や再割り込みを発生させる処理（delay() など）は強制停止につながる
  • printf は非推奨

詳細実装

Clog 実装詳細

  • 各 project ごとに Logger.hpp を配置し設定と API 提供が行われる
  • マクロ API はコンパイル時とランタイム時の二段階で検証を行う
  • cTag（Color Tag）により色付きログを実現する
  • 現状は自由度が高すぎるため今後変更予定

CanSystem 実装詳細

インターフェース設計:

  • ICanController: CAN/FDCAN 共通の基本インターフェース
  • IFdcanMgr: FDCAN 固有機能
  • ICanMgr: CAN 固有機能

実装構造:

  • CanInterfaces.hpp: 全関数プロトタイプ
  • abstract/: 実装コード（命名変更予定）
  • impl/: profile 定義（CAN 割り込み設定、TxHeader、sFilterConfig）

デフォルト profile:

  • CAN: 全 ID パス設定
  • FDCAN: 全 ID パス設定
  • FDCAN 互換 CAN: 全 ID パス設定

カスタム profile: 新規作成するか、既存 profile の config を取得・編集・再適用する

ライブラリ内使用

  • ICanController&: CAN/FDCAN 共通機能（推奨）
  • IFdcanMgr& または ICanMgr&: プロトコル固有機能を追加利用可能

ICanController を使用することで CAN/FDCAN に依存しない汎用ライブラリを実現できる。
